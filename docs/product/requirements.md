# REM — Product requirements and P1 acceptance criteria

**Owner:** Lead (product) · **Status:** Specified (P0 draft r1, 2026-11-24) · **Governed by:** [PROJECT_SPEC.md](../../PROJECT_SPEC.md), [FEATURE_REGISTRY.md](../../FEATURE_REGISTRY.md)

This file is the single home of REM scope, non-goals, status vocabulary, enterprise deviations and **P1 acceptance criteria**. The traceability, packets and verification for each ID are in [backlog.md](../plan/backlog.md). Telegram evidence is in [reference-behavior.md](reference-behavior.md). Capability IDs come from the registry and are never reused.

## 1. Scope and non-goals

**In scope (P1):** a deployable, single-tenant, self-hosted messaging foundation. It covers invite-based identity, sessions and devices, direct and group chats, the message lifecycle, durable offline sync on web (React/TypeScript + Rust WASM) and desktop, basic files, basic admin, backup/restore and operator tooling. Later phases follow [PROJECT_SPEC §6](../../PROJECT_SPEC.md#6-phase-strategy-and-explicit-gates).

**Non-goals (all phases unless the PO decides otherwise):** Telegram protocol (MTProto) compatibility, Telegram accounts or cloud, server emulation, federation, and Telegram bridging. Also excluded are Telegram trademarks or assets, public social-network operation, global discovery by default, a crypto/gift economy, mandatory SaaS, always-online license checks, and any E2EE claim before ADR-0009 conditions are met.

**Non-goals for P1 specifically:** mobile apps (P3), calls (P3), SSO/SCIM (P3), channels (P2), topics (P2), reactions (P2), server-side thumbnails/transcoding (P2/P3), multi-node HA (P3), multi-tenant SaaS (separate decision), phone-number identity.

## 3. Status vocabulary (four separate measures)

A capability or requirement row carries one **lifecycle** value: `Discovered → Specified → Reviewed → Implemented → Verified → Released`. Optional flags are `UNKNOWN`, `BLOCKED` and `DEVIATION`. Reference evidence strength is separate: `OFFICIAL | OBSERVED | INFERRED | UNKNOWN`. The four measures stay distinct and are never merged into one percentage:

1. **Reference coverage**: evidence rows in [reference-behavior.md](reference-behavior.md).
2. **Implementation**: lifecycle reaches `Implemented`, linked to an immutable commit.
3. **Verified correctness**: `Verified` needs a reviewed contract, passing relevant gates at a recorded SHA and acknowledged limitations ([registry release rule](../../FEATURE_REGISTRY.md#release-completeness-rule)).
4. **Operational/commercial readiness**: tracked in [operations.md](../operations.md) and [commercial.md](../commercial.md).

## 5. P1 acceptance criteria

Criteria are numbered `<ID>.a`, `<ID>.b`, and so on. Those numbers are the traceability anchors that test names cite. **Cross-cutting criteria XC-1..XC-8 apply to every P1 ID** and are not repeated:

- **XC-1 Authorization:** the server checks every command and read against current membership and role. A non-member receives `not_found`, never `forbidden` that confirms the object exists.
- **XC-2 Offline/retry:** every idempotent mutating command, from sends to prefs and membership changes, carries `operation_id` and records its idempotency result in the same transaction as its effect. The table in [contracts.md §2.1](../architecture/contracts.md#21-idempotent-mutations-and-operation-lookup) is the only list of mutating endpoints: it gives each one's key and canonical fields, and names each command that is not idempotent with its reason. A retry returns the original result. Reusing the id for a different command returns `operation_conflict` (SYN-002).
- **XC-3 Realtime:** each state change is a sequenced event ([sync.md](../architecture/sync.md)). Clients converge after duplicates, reordering and reconnects.
- **XC-4 Multi-platform:** the behavior works in the supported web browsers and on desktop, by keyboard alone, at a 320 px width, with IME input.
- **XC-5 Resilience:** a timeout, a disconnect or a server restart never loses a committed effect or duplicates one.
- **XC-6 Privacy:** no message bodies, tokens, passwords or file names in logs or metrics ([threat-model.md](../security/threat-model.md#5-data-classification-and-logging)).
- **XC-7 Operations:** a schema change ships with forward migration and a documented rollback.
- **XC-8 Verification:** each criterion maps to a named test at the cheapest sufficient tier ([testing-ci.md](../engineering/testing-ci.md#2-test-ladder-applied-to-rem)).

Numbers marked *policy* are org-configurable defaults. A value marked *TBD-measure* is fixed only after a measured baseline (OPS-009) and is never invented.

### Identity (ID)

Concurrent redemption never exceeds the use limit. c) Onboarding sets a display name and a policy-compliant password and registers the first device. d) Invite tokens have ≥128 random bits, are stored hashed and are never logged. It then deletes that user's local store on the device, unsent operations included. c) A password change revokes the other sessions by default. d) An admin-initiated reset creates a single-use, expiring link. Without SMTP an admin receives it, after a different admin (neither the actor nor the target) approves when `require_dual_approval` is on (ENT-012.a). | ID-003 | a) The user lists their own sessions with device name, platform, created time and last-active time. b) Revoking a session commits server-side. That session's open sockets close and its later requests fail with `session_revoked` within *TBD-measure* seconds. c) A revoked client clears its credentials and says that unsent items were not delivered yet and will be sent after that user signs in again on that device. Until then the local store stays dormant ([sync.md §5.4](../architecture/sync.md#54-store-identity-and-browser-storage), PO-Q10 interim default). d) An org admin can revoke the sessions of accounts of strictly lower rank only ([threat-model §4.1](../security/threat-model.md#41-rank-direct-chats-and-ownership-continuity)). e) Idle sessions expire per *policy* (ADR-0010). |

Their content stays and is labelled as a deactivated user. c) The join policy is invite-only in P1. Domain auto-join waits for SSO (ID-009, P3). |
| ID-006 | a) An org admin deactivates and reactivates accounts of strictly lower rank only. A deletion request is approved per *policy* by an org admin who outranks the account (DEV-02, [threat-model §4.1](../security/threat-model.md#41-rank-direct-chats-and-ownership-continuity)). b) Deletion erases profile PII, revokes sessions and tombstones the author label. Messages follow retention. c) A user can export their profile and their own messages as a JSON archive. The archive is built asynchronously, served behind authorization and its link expires. |

### Direct chat (DM)

| ID | Acceptance criteria |
|---|---|
| DM-001 | a) Opening a DM between two org members is idempotent: one DM per pair. b) Text holds up to a *policy* length. Formatting is typed entity ranges (bold, italic, underline, strikethrough, inline code, code block, link, mention), with offsets in UTF-16 code units (ADR-0006). The server rejects overlapping or out-of-range entities. c) Rendering never interprets HTML or script, and XSS payload fixtures render inert. d) Empty or whitespace-only bodies are rejected. |
| DM-002 | a) Visible states are `pending`, `sent` (ACK with a sequence number), `read` and `failed` (retryable or permanent). b) A pending message survives an app restart or browser reload. c) After a lost ACK, a retry with the same `operation_id` yields the same `message_id`, and no device shows a duplicate. d) A permanent failure shows the reason and offers retry or discard. |
| DM-003 | a) A reply targets an existing message the sender can read in the same conversation. A deleted target renders as a placeholder (DM-003-R01). b) Only the author edits, within a *policy* window. Each edit creates revision n+1 and marks the message edited (R02). c) An edit carries `expected_revision`. A stale value returns `revision_conflict` with the current revision, so no update is silently lost (R03). d) An edit reaches all authorized devices and updates search and unread state (R04). e) Retrying the same edit operation creates no extra revision (R05). f) Revision history is retained per DEV-03 (R06). g) Accessibility and compact layout follow UX-005 and UX-001 (R07). |
| DM-004 | a) Delete-for-self hides the message on all of the user's own devices. b) Delete-for-everyone is allowed to the author within a *policy* window, and to group admins with that right over members of lower rank (GRP-004.e). It emits a tombstone event, and synced devices remove the content. c) The deleted body leaves search and primary storage per DEV-04. |
| DM-005 | a) Forwarding creates a new message in the target conversation with attribution. The original author is always kept, unless *policy* hides attribution (d). The source conversation and message are given only to a reader who can see the source, and are otherwise unavailable ([contracts.md §2.2](../architecture/contracts.md#22-visible-ranges-event-pages-and-redacted-stubs)). b) It needs read access to the source and post permission in the target. c) Attachments are referenced, not copied, and access is re-checked per target. d) Forwarding without attribution is allowed when org *policy* permits it. |
| DM-006 | a) A permitted role pins and unpins messages. Pins are ordered, sequenced events visible to members. b) "Saved messages" is a personal self-conversation that can receive forwards. Bookmarks and tags stay in ORG-006 (P2). |
| DM-008 | a) Typing indicators are ephemeral, never persisted and carry no sequence. b) The client sends at most one per 3 s per conversation, and the server drops any excess. c) An indicator expires after 6 s without a refresh. d) Only current members receive them. |
| DM-009 | a) Read position is the highest sequence read per user per conversation. It only moves forward, and concurrent device updates converge to the maximum. The server clamps it to the reader's highest visible seq. b) Unread count is the number of messages by others above the read position, excluding deleted ones. It agrees across devices after sync. c) In a DM, the sender sees `read` once the recipient's position reaches the message. In a group, `read` means at least one other member has read it. Authors learn both through `receipt.updated`: the reader's position in a DM, `read_by_count` and `up_to_seq` in a group, coalesced and rate-limited (*policy*, [contracts.md §3](../architecture/contracts.md#3-event-catalog-conversation-stream-unless-noted-all-schema_version-1)). Per-member read lists are capped by *policy*; the reference caps them at 100 members and 7 days. Hiding read receipts is P2 (ID-012). |
| DM-012 | a) A mention entity references a `user_id`, and members mentioned get a mention badge (NTF-001). b) The client detects URLs and hashtags and stores them as entities. c) Server-side previews are off by default (DEV-05). With previews enabled, fetching meets the SSRF controls of SEC-010. d) Hashtags are searchable through ORG-004. |

| GRP-004 | a) There is exactly one owner, plus admins with granular rights. b) Promote and demote are sequenced, audited events. c) Ownership transfer needs the owner's re-authentication. ### Sync and realtime (SYN)

Normative design: [sync.md](../architecture/sync.md). Criteria here are what the tests must show.

| ID | Acceptance criteria |
|---|---|
| SYN-001 | a) The WebSocket authenticates with a short-lived ticket obtained over HTTPS. No long-lived token appears in any URL. b) Heartbeat timeouts and reconnects use exponential backoff with jitter. c) After a reconnect, the client completes catch-up before it trusts pushed events. d) The server closes sockets of revoked sessions. e) Protocol negotiation follows SYN-013. |
| SYN-002 | a) The client generates `operation_id` (UUID) and the server assigns `message_id` (UUIDv7). b) An idempotency record is kept for at least `IDEMPOTENCY_TTL` plus `SAFETY_MARGIN` (*policy*, defaults 30 days and 2 days). A duplicate returns only the stored original ACK fields with `duplicate=true`, even if the actor's membership was removed since. A revoked session gets `session_revoked`, even for a duplicate ([sync.md §3](../architecture/sync.md#3-server-write-path-durable-ack)). c) The server hashes the canonical command it builds after parsing, never the raw request bytes ([contracts.md §2.1](../architecture/contracts.md#21-idempotent-mutations-and-operation-lookup)), so a re-encoded retry of the same command is a duplicate. The same id under the same key (the session key, or the token key of a pre-session command, [contracts.md §2.1](../architecture/contracts.md#21-idempotent-mutations-and-operation-lookup)) with a different command, of any kind or target, returns `operation_conflict`. The same id with another token is a different key, so it is a new command. d) `GET /v1/operations/{operation_id}` returns the stored result for the caller's own device. After `operation_conflict` the client fetches it and reconciles, and never resends under a new id automatically. e) Every idempotent command kind in the [contracts.md §2.1](../architecture/contracts.md#21-idempotent-mutations-and-operation-lookup) table has a duplicate test and a conflict test. |
| SYN-003 | a) Within a conversation, sequence numbers are contiguous from 1 with no gaps or repeats, including under concurrent senders and aborted transactions. b) A property test with N concurrent writers yields exactly 1..N. |
| SYN-004 | a) The ACK is sent only after the message, event, idempotency record and outbox row commit together. b) Fault injection: a crash before commit leads to exactly one message after retry. A crash after commit but before the ACK leads to the same result on retry. c) The dispatcher delivers at least once and resumes after its own crash. |
| SYN-005 | a) The client reducer is deterministic. Applying an event twice equals applying it once. b) From any valid snapshot, applying events in sequence order gives the same state. A property test covers duplicated, reordered and dropped deliveries. |
| SYN-006 | a) Each device persists its user cursor and, per conversation, a `covered_through` cursor. The initial cursor is the start of the reader's first visible range minus 1. b) Paginated catch-up returns, after the cursor, every seq inside the reader's visible ranges, each once, as the full event or a payload-free `redacted` stub. Pages carry `covered_from`, `covered_to` and `visible_ranges` ([contracts.md §2](../architecture/contracts.md#2-http-surface-p1-v1)). c) After catch-up, the local projection equals the server projection in a model-based test. d) `conversation_heads` lists only conversations where the user is currently a member, plus one final head capped at `left_seq − 1` for each conversation whose leave event (`user.membership_changed`) has a `user_seq` above the request's `user_cursor` ([sync.md §4](../architecture/sync.md#4-catch-up-and-realtime)). Tests: a final head while the cursor is below the leave event; no head once the cursor is at or past it, or for a conversation never joined. |
| SYN-007 | a) A pending operation is persisted before the UI shows it. b) Each conversation drains its queue first-in, first-out. Retries use capped backoff with jitter. Every error code maps to one outbox class (retryable, permanent, reconcile, session-terminal, paused or sync-reset) per [sync.md §5](../architecture/sync.md#5-client-outbox-and-pending-state). c) The queue survives a restart. Each pending operation stores `created_after`, the `server_time` of the latest response seen before it was created. Its age is a fresh `server_time` minus `created_after`, so the device clock is never used ([sync.md §5.3](../architecture/sync.md#53-expiry-and-stuck-operations)). Automatic retry stops at `IDEMPOTENCY_TTL` minus `SAFETY_MARGIN` (*policy*, default margin 2 days), and the operation is then shown as needing confirmation. Tests with ±24 h client clock skew, and with the clock changed while offline, never retry automatically past that cut-off. d) An operation that references a not-yet-ACKed local message (edit, delete, pin, reply, forward) waits for that message's ACK, across conversation queues, and is sent with the server `message_id`. An edit or delete of an unsent message folds into the pending send. When a source leaves `pending` without an ACK, its dependents end with it, transitively: `failed(stuck)` after a stuck source, `expired` after an expired one, and `failed(dependency_failed)` after any other failure, a discard or a folded delete ([sync.md §5.2](../architecture/sync.md#52-dependent-operations)). A user retry puts the operation at the tail of its conversation queue, and its dependents after it. e) A retryable operation that fails N times (*policy*, default 20), or keeps failing for T (*policy*, default 24 h) measured in server time from its first failed attempt, becomes `failed(stuck)` with retry and discard ([sync.md §5.3](../architecture/sync.md#53-expiry-and-stuck-operations)). Its dependents end with it (d), so none holds a queue position past the stuck bound. The conversation queue then continues, and the UI says the order may differ ([ux.md §2](ux.md#2-state-model-shown-to-users)). |
| SYN-008 | a) A gap exists only inside a visible range: the client expects the next visible seq after `covered_through`, never local + 1 across an invisible span. A gap triggers a range fetch. b) A cursor below a retention floor returns `cursor_expired`: `min_retained_seq` for a conversation stream, `min_retained_user_seq` for the user stream. A conversation reset rebuilds from the conversation read endpoints. A user-state reset rebuilds the membership list from `GET /v1/conversations`, then resets every cached conversation ([sync.md §4](../architecture/sync.md#4-catch-up-and-realtime)). Both keep the pending operations. After a reset the client never shows a stale revision, or a message deleted for everyone, from the pruned span. c) A corrupt or unmigratable local store is detected and recovered through the reset path. d) After a rejoin, `user.membership_changed` carries `joined_seq`, `left_seq` and the new interval's `history_visibility`, and the client then refreshes `visible_ranges` from `GET /v1/conversations/{id}`. Under `from_join` the span it was absent for is not a gap. Under `full` that span becomes visible: the client lowers `covered_through` to the lowest added range start minus 1 and pages again, and re-applied events are duplicates ([sync.md §4.1](../architecture/sync.md#41-cursors-and-gap-detection)). |
| SYN-009 | a) A removed member never receives events at or after `left_seq`, over catch-up or push, even with a forged cursor (negative test). b) History visibility follows GRP-007.a: each membership interval keeps the setting it opened under. A former member's event pages report `last_seq` and `covered_to` capped at `left_seq − 1`, and a request past that returns an empty page with the same caps, so paging ends and reveals no later progress ([sync.md §6.1](../architecture/sync.md#61-visible-ranges)). c) A former member gets no new attachment URL through that conversation, for messages before or after the removal (MED-010.c). d) A send and a removal on the same conversation are serialized ([sync.md §3](../architecture/sync.md#3-server-write-path-durable-ack)). e) Events that reference a message (edit, delete, pin, reply quote, forward source) follow the visibility of that message's creation seq for the reader. When it is not visible, edit, delete and pin events arrive as `redacted` stubs, a reply quote or a forward's source renders as "Message unavailable" ([ux.md §2](ux.md#2-state-model-shown-to-users)), and a request for that message id returns `not_found`. A forward still keeps its original author (DM-005.a). f) Push is authorized per event and recipient ([sync.md §3.3](../architecture/sync.md#33-push-path-ordered-dispatch-and-fanout-authorization)). A commit with an unknown outcome never re-admits a removed member or a revoked session to push. Tests: a member removed at seq `r` never receives `r + 1` over push; a revoked session receives no push after the revocation commits; after a removal or a session revocation whose commit outcome is unknown, the member or session stays denied until the cache is rebuilt from the database; after the rebuild, a still-authorized session receives `head` and fills the gap it missed. |
| SYN-010 | a) A read position is a monotonic maximum, clamped per DM-009.a. b) It reaches the user's other devices through `user.read_position`, and message authors through `receipt.updated` (DM-009.c). |
| SYN-011 | a) Presence and typing go through the `Presence` port, using an in-process adapter in P1 (ADR-0011). b) Nothing is persisted, and loss on restart is accepted. c) Fan-out and rate are bounded. |
| SYN-013 | a) Client and server negotiate a protocol version, and the server supports the current and previous minor version. b) Golden JSON fixtures per version pass in CI. c) Unknown fields are ignored, and unknown event types are stored as unsupported without a crash. d) A client below the minimum gets `upgrade_required`. |
| SYN-014 | a) The test harness injects clock skew (±24 h), duplication, reordering, drops and delay. b) Ordering relies only on sequence numbers, never on client clocks. c) Timeouts use a monotonic clock. |

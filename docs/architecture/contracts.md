# REM — API, event and binding contracts (v1 draft)

**Owner:** Architecture (protocol) · **Status:** Specified (P0 r2, 2026-11-24, with the round-2 resolutions LD-17..LD-38 in [decisions.md](../plan/decisions.md#2-lead-decisions-reversible)). Golden fixtures are produced in packet P1-04. **Semantics:** [sync.md](sync.md). **Authorization:** [threat-model §4](../security/threat-model.md#4-authorization-matrix-p1). **Decisions:** ADR-0006 in [adr.md](adr.md#adr-0006-wire-format-and-versioning).

## 1. Versioned boundaries

| Boundary | Version carrier | Compatibility rule |
|---|---|---|
| HTTP API | path prefix `/v1/`, header `REM-Client-Version` | The server supports the current and previous minor version. A breaking change means `/v2/` running alongside. |
| WebSocket | subprotocol `rem.v1` plus `hello.protocol` | Negotiate the highest common version, otherwise `upgrade_required`. |
| Event payloads | `schema_version` per event `type` | Additive changes keep the version. A breaking change bumps it, and both versions are emitted during the window. |
| WASM binding (TS API) | `BINDING_VERSION` constant plus the npm package version | The web app pins one exact SDK build, so they ship together. |
| Native FFI (UniFFI, after P1) | crate version | Same rule as WASM. |
| Client local store | `local_schema_version` | Forward migrations. On failure, the SYN-008 reset. |
| Server database | migration version (sqlx) | Expand/contract (OPS-002). |

Wire format: JSON (UTF-8) for v1. It is debuggable, easy for browsers, and has golden fixtures. A binary encoding is a later ADR, adopted only if PT-02 or OPS-009 shows payload cost matters. Text entity offsets are in **UTF-16 code units**, matching both the JS strings the UI edits and the reference model ([reference DM-001](../product/reference-behavior.md#reference-table)). Rust converts at the edge.

The snapshot resets ([sync.md §4](sync.md#4-catch-up-and-realtime)) read state, not the event log. The user-state reset pages `GET /v1/conversations`. The conversation reset reads `GET /v1/conversations/{id}`, the `…/members` roster and `…/messages` history pages. Their shapes are in §2.2.

**Login and device binding** ([sync.md §5.4](sync.md#54-store-identity-and-browser-storage)). `device_id` is a UUIDv7 that the server assigns at a store's first login. Before its first login a store persists a client-generated `device_nonce` (UUIDv4). `POST /v1/sessions` carries the credentials and, when the store holds one, its bound `device_id`; a store with no bound `device_id` sends its `device_nonce` instead. If that device is registered to this user and not retired, the new session binds to it. Otherwise the server registers a new device, at most one per `(user_id, device_nonce)`, so a retried new-device login binds to the device the first attempt registered. Either way there is no error, and the response returns the bound `device_id`, so the call is no oracle for device ids. Each session has exactly one device, and creating a session for a device revokes that device's previous session with reason `replaced` (§3). `device_id` therefore stays the same across a re-login. The first login response after an admin-initiated password reset carries `notice: "password_reset_by_admin"`. `GET /v1/sessions` lists the user's unrevoked sessions `{session_id, device_id, created_at, last_seen_at, current}`, where `current: true` marks the caller's own session, so a client that lost its store can still find it. **Eviction recovery:** a client whose store was lost calls `DELETE /v1/sessions/{id}?reason=device_lost` on its current session, which retires that device for good, and then logs in from a new store, with that store's new `device_nonce` and no `device_id`. Only the caller's own current session may be revoked with `reason=device_lost`; on any other session the server returns `forbidden_action`, so no other session and no admin can retire a device.

### 2.1 Idempotent mutations and operation lookup

- **Mutation table.** This is the only list of mutating endpoints. Each idempotent command records its idempotency record in the same transaction as its effect ([sync.md §3.2](sync.md#32-idempotency-for-every-mutation)). The serializing row is the row lock that orders the command; the rows after it are locked next. All locks follow the global order in [sync.md §3.1](sync.md#31-lock-order-user-sequence-and-retries): device rows come first, and every session command takes the actor's session row in its ascending-id place among the session rows it locks, after any device rows and before all other rows. Key **session** is `(actor_user_id, device_id, operation_id)`. Key **token** is `(token_hash, operation_id)`, where `token_hash` is the stored hash of the credential the command redeems (an org invite honors its `max_uses`, so it may be redeemed more than once).

- **Target.** The record's `target` is the object the path names: the actor's user for `/v1/me…`, and the record the token resolves to for a token path. An endpoint whose path names no object creates its target: `target` is the created id (the organization for bootstrap), written after creation, and the conflict check then compares only kind and hash.
- **Canonical hash.** SHA-256 over the RFC 8785 (JCS) encoding of the row's canonical fields, taken after the server's own validation of each field. The only normalization is NFC on `display_name` (ID-004.a); every other string is hashed as received. A message `body` is hashed as the received code points and is never transformed, because entity offsets depend on it. Id lists are sorted, and `entities` are sorted by (`offset`, `length`, `type`), with ties broken by the JCS encoding of the whole entity. `read.set` hashes `seq` as received, before the server clamps it, so a retry still matches after visibility changes. For a create-style command, omitted optional fields take their defaults; `PUT …/prefs` replaces all four prefs and is create-style. For a `PATCH` or other partial command, only the fields present are hashed, an explicit `null` is kept, and an omitted field (meaning unchanged) is not filled in. Secrets (passwords, tokens) are never canonical fields. Raw request bytes are never hashed, so a client that re-encodes a pending op after an upgrade still matches. The record stores the kind, the target, this hash and the stored result.
- **Replay and conflict.** The same key with the same kind, target and hash returns only the stored original result plus `duplicate: true`, never new data. The same key with a different kind, target or hash returns `operation_conflict`. An `operation_id` is unique only within its key: the same id with a different token is a different key, and therefore a new command.
- **Token commands** look up their record before they validate the token ([sync.md §3.2](sync.md#32-idempotency-for-every-mutation)), so a replay after the token was consumed still returns the stored result. Once the record is pruned ([sync.md §7](sync.md#7-evolution-retention-and-clocks)), the consumed token returns `invite_invalid`, as for any used token.
- **Stored results** never hold a secret or a session. A pre-session command stores `{organization_id, user_id}` (bootstrap) or `{user_id}` (invite and reset redemption), and its response carries no session: the client then logs in (§2). A replay of a command that issued a token returns the record's id without the token: a link token can be re-read through `GET …/links`, and a lost org invite is revoked and created again. Because secrets are not canonical fields, a `password_reset.redeem` replay with a different new password returns the stored result with `duplicate: true` and never applies that password.
- **Approvals.** When `require_dual_approval` is on, five changes store a pending approval as their effect and return its `approval_id`: granting org admin, an admin-delivered reset link and an admin-delivered onboarding-token re-issue (all `PATCH /v1/admin/users/{id}`; the re-issue uses the `reset_link` kind), a break-glass reassignment (`POST /v1/admin/conversations/{id}/owner`), and turning `require_dual_approval` off (`PATCH /v1/admin/policies`). Turning it on, and deactivating, deleting or demoting an org admin while it is on, return `forbidden_action` when fewer than two active org admins would remain (ENT-012.a). Each of these commands locks the organization's policy row `FOR UPDATE`, last in lock order, and counts the active org admins under that lock, so concurrent changes cannot together leave one. A deletion request (`POST /v1/me/deletion-request`) always stores one, approved per *policy* by an org admin of strictly higher rank than the account (ID-006.a, DEV-02). `POST /v1/admin/approvals/{id}/approve` applies the change ([threat-model §4.2](../security/threat-model.md#42-admin-recovery-powers-po-q9)). Under its locks it re-evaluates every precondition of the stored change: the approver is neither the actor, nor the account the change acts on (the current GO for a break-glass), nor the new owner of a reassignment; for `account_deletion` the approver outranks the account, and for every other kind the actor is still an admin of strictly higher rank than the account; that GO is unchanged and not deactivated; the new owner is still a current, active member. If any fails, or the approval has expired, it returns `forbidden_action` and the change has no effect. A pending approval expires after a *policy* interval.
  - **Approval resource:** `{approval_id, kind, actor_id, target, created_at, expires_at, status}`, with `kind` one of `grant_org_admin`, `reset_link`, `reassign_owner`, `disable_dual_approval`, `account_deletion` and `status` one of `pending`, `approved`, `link_issued`, `declined`, `expired`. `target` is the account the change acts on, or the conversation for `reassign_owner`, whose record also carries `current_owner_id` and `new_owner_id`. `GET /v1/admin/approvals` lists the approvals the caller may approve or initiated; `GET /v1/admin/approvals/{id}` reads one ([threat-model §4](../security/threat-model.md#4-authorization-matrix-p1)).
  - **Reset link delivery without SMTP:** the link goes only to the original actor, never to the approver, and only in one response. With dual approval off it is in the `PATCH /v1/admin/users/{id}` response. With it on, the approve applies the rest of the change, and the actor then calls `POST /v1/admin/approvals/{id}/link`, which issues the link and returns it; the server stores only its hash. Under its locks it re-checks that the caller is the original actor, still of strictly higher rank than the target, and that the target is active; it succeeds only on an `approved` `reset_link` approval, which it moves to `link_issued`, and otherwise returns `forbidden_action`. An `approved` `reset_link` approval with no link issued within the same *policy* interval becomes `expired`. A replay of either returns the stored result without the link, so a lost response needs a new reset. With SMTP configured no response carries the link.
- **Self conversation.** No endpoint creates it. The account-creating transaction (bootstrap, invite redemption, `admin.user_create`) creates it, one per user ([sync.md §3.2](sync.md#32-idempotency-for-every-mutation)).
- **Open DM.** `POST /v1/conversations` with `kind: "dm"` for a pair that already has a DM returns that conversation with `created: false`. The pair is unique per organization ([architecture.md §4](architecture.md#4-domain-model-sketch-validated-against-invariants-not-a-final-schema)).
- **`GET /v1/operations/{operation_id}`** returns `{operation_id, kind, target, ack}` from the record of the caller's own user and device. It serves session commands only; a pre-session op settles by replay. It returns `not_found` when this device has no recorded effect under that id (never applied, or past retention, [sync.md §7](sync.md#7-evolution-retention-and-clocks)). The client calls it after `operation_conflict` and to settle a pending op without resending ([sync.md §5](sync.md#5-client-outbox-and-pending-state)).

### 2.2 Visible ranges, event pages and redacted stubs

- **`visible_ranges`** is the reader's list of half-open `[from_seq, to_seq)` pairs, with `to_seq: null` for an open range. The server computes it from the reader's membership intervals, each with the `history_visibility` recorded when it opened ([sync.md §6.1](sync.md#61-visible-ranges)). It is returned by `GET /v1/conversations/{id}`, every conversation-list entry, every event page and every history page.
- **Event page** (`GET /v1/conversations/{id}/events?after=S&limit=N`):

  ```json
  { "conversation_id": "0192…", "covered_from": 1001, "covered_to": 1100, "last_seq": 1250,
    "visible_ranges": [[1, 900], [1001, null]], "events": [ … ] }
  ```

  `covered_from` is `S + 1` and `covered_to` is the highest seq the page accounts for, so the client stores `covered_to` as its `covered_through` cursor ([sync.md §4](sync.md#4-catch-up-and-realtime)). For a current member, each seq in `[covered_from, covered_to]` that lies inside a visible range appears exactly once, as a full event or a redacted stub. Seqs outside visible ranges are absent and are not gaps, so a page may advance `covered_to` without returning events. More pages remain while `covered_to < last_seq`. For a former member, `last_seq` and `covered_to` are capped at `left_seq − 1` of their final leave, and a request at or past that cap returns an empty page with the same caps, so paging ends and no later progress shows.
- **Conversation list** (`GET /v1/conversations?after=&limit=`): each page carries `as_of_user_seq`, the user's `last_user_seq` read in the same database snapshot as the page's entries, so no user event between them is skipped by the replay. Each entry carries `conversation_id`, `kind`, the current membership interval (`joined_seq`, `left_seq`, and that interval's `history_visibility`), `visible_ranges`, `last_seq`, `read_seq` and the prefs. The user-state reset uses it ([sync.md §4](sync.md#4-catch-up-and-realtime)).
- **Former members** see content as of `left_seq − 1` of their final leave in state, event pages and history pages ([sync.md §6.1](sync.md#61-visible-ranges)): each message at its last revision committed before `left_seq`, and pins and settings as of that seq. A message deleted for everyone at any time is a tombstone with no deletion time (DEV-04). On event pages, for every reader, the `message.created` and `message.edited` events of such a message carry the payload `{message_id, deleted: true}` with no body, entities or attachments, so a reader whose page ends before the `message.deleted` event still sees only the tombstone. When the message's creation seq is not visible to the reader, the redacted stub below applies instead, and no `message_id` is sent.
- **Conversation state** (`GET /v1/conversations/{id}`): a former member gets the state capped at their final leave (`last_seq` at `left_seq − 1`, `visible_ranges` as at that leave). A deleted conversation returns `not_found` for its state, event pages, history pages and roster.
- **Roster** (`GET …/members?after=&limit=`): each page carries `as_of_seq`, the conversation's `last_seq` when it was read, and `members` entries `{user_id, role, rights, joined_seq, timeout_until}`. `next_after` is `null` on the last page.
- **History page** (`GET …/messages?before=<seq>&limit=N`): `before` is an exclusive creation seq, and an absent `before` means the newest page. The page returns visible messages newest first, each at its current revision (for a former member, as above). A message deleted for everyone is a tombstone `{message_id, seq, deleted: true}`; a message hidden for self is omitted; references follow the rule below. `limit` counts tombstones. Seqs outside `visible_ranges` are skipped, so one page may span an invisible gap.

  ```json
  { "conversation_id": "0192…", "as_of_seq": 1250, "visible_ranges": [[1, 900], [1001, null]],
    "messages": [ { "message_id": "0192…", "seq": 1240, "revision": 2, "body": "…", … },
                  { "message_id": "0192…", "seq": 1236, "deleted": true } ],
    "next_before": 1236 }
  ```

  `as_of_seq` is the conversation's `last_seq` when the page was read (capped like `last_seq` for a former member). `next_before` is the `before` of the next older page, and `null` once the page reaches the start of the lowest visible range. Each message entry carries `revision`. A page can be older than state the client already applied, so the client merges by the higher `revision`, and a tombstone or a hide for self is terminal: a page never restores a row's older revision, its body after a delete for everyone, or a row hidden for self. The span each page is authoritative for, and how the client drops cached rows the page omits, are in [sync.md §4](sync.md#4-catch-up-and-realtime).
- **Redacted stub:** `{ "seq": 1043, "type": "redacted" }`, with no other field (no actor, time, original type or payload). The server sends one in place of (1) `message.edited`, `message.deleted`, `message.pinned` or `message.unpinned` when the referenced message's creation seq is not visible to the reader, and (2) `link.*` or `join_request.*` events to members without the matching right (§3). Over WebSocket it travels as `{conversation_id, seq, event}` like any other event.
- **Referenced messages:** in `message.created` and in history pages, `reply_to` becomes `{ "unavailable": true }` when the referenced message is not visible to the reader. `forwarded_from` is `{author_id, conversation_id, message_id}`. It always keeps `author_id` (DM-005.a). A forward sent with `attribution: false`, which *policy* must permit (DM-005.d), carries no `forwarded_from`. When the reader cannot see the source, the two source ids are replaced by `"unavailable": true` ([sync.md §6.2](sync.md#62-referenced-messages-and-scoped-events)). A request naming an invisible message id returns `not_found`.
- **`GET /v1/sync?user_cursor=U&limit=N`** returns `user_events` after `U`, `conversation_heads` and `min_retained_user_seq`. Each head is `{conversation_id, last_seq}` for a conversation where the user is currently a member. A conversation the user has left gets instead one final head `{conversation_id, last_seq: left_seq − 1, left: true}` while its latest leave event (`user.membership_changed`) has a `user_seq` above `U`, so a conversation has at most one head (rules in [sync.md §4](sync.md#4-catch-up-and-realtime)). A request with `U < min_retained_user_seq − 1` returns `cursor_expired` with `detail.stream = "user"` (§4).

## 3. Event catalog (conversation stream unless noted, all `schema_version: 1`)

`message.created`, `message.edited`, `message.deleted` (tombstone), `message.pinned`, `message.unpinned`, `conversation.created`, `conversation.updated`, `conversation.deleted`, `member.added`, `member.removed`, `member.role_changed`, `member.restricted`, `link.created`, `link.revoked`, `join_request.created`, `join_request.resolved`. On the user stream: `user.membership_changed`, `user.read_position`, `user.prefs_changed`, `user.profile_changed`, `user.session_revoked`, `user.message_hidden` (delete-for-self), `user.join_request_resolved`, `receipt.updated`. Ephemeral, never sequenced: `typing`, `presence`.

Envelope (matches the PDF discovery sketch, with `seq` naming):

```json
{ "event_id": "0192…", "conversation_id": "0192…", "seq": 1042, "type": "message.created",
  "schema_version": 1, "actor_id": "0192…", "device_id": "0192…", "operation_id": "6f1c…",
  "server_time": "2026-11-24T08:00:00Z", "payload": { "message_id": "0192…", "body": "…", "entities": [] } }
```

`operation_id` and `device_id` appear only to the actor's own devices. Other recipients get the envelope without them, which hides device metadata.

**WebSocket frames.** The server pushes `{conversation_id, seq, event}` and `{user_seq, user_event}`. The client sends `hello {protocol, client_version, device_id, user_cursor}` and `typing`. A `hello` whose `device_id` is not the session's bound device is refused with `unauthenticated`. The server also sends `head {conversation_id, last_seq}`, which is not sequenced: `Fanout` sends it, after it rebuilds authorization-cache entries, to every still-authorized connected session of each affected conversation ([sync.md §3.3](sync.md#33-push-path-ordered-dispatch-and-fanout-authorization)). The client treats it like a head from `GET /v1/sync` and runs gap detection from its `covered_through` ([sync.md §4.1](sync.md#41-cursors-and-gap-detection)).

**Reader-scoped payloads** (rules in [sync.md §6](sync.md#6-revocation-and-history-authorization)):

- `link.created` and `link.revoked` carry `link_id` and metadata (expiry, use limit, use count, approval required), never the token. No event carries an invite or link token. The token is returned only in the `POST …/links` response to its creator and by `GET …/links` to holders of the link right, which lists active links only and reads the token from a copy encrypted at rest; that copy is deleted when the link is revoked, expires or reaches `max_uses` ([threat-model §5](../security/threat-model.md#5-data-classification-and-logging)).
- `link.*` payloads reach holders of the link right and `join_request.*` payloads reach holders of the approve right. Other members receive redacted stubs at those seqs (§2.2).
- `user.membership_changed` carries `conversation_id`, `joined_seq`, `left_seq` (`null` while a member) and the `history_visibility` recorded when that interval opened, so a client knows where a new visible range starts after a rejoin. A later `history_visibility` change is a `conversation.updated` and changes no existing interval ([sync.md §6.1](sync.md#61-visible-ranges)).
- `user.session_revoked` goes to the user's other sessions: `{session_id, device_id, reason}`. `reason` is one of `logout` (the session's own logout), `revoked_by_user`, `revoked_by_admin`, `password_changed`, `password_reset`, `deactivated`, `replaced` (a new login on the same device, §2), `device_lost` (eviction recovery, §2) or `expired` (idle timeout). Nothing is pushed to a session after its revocation (I10), so the revoked session learns the reason from the `session_revoked` error (§4).
- `receipt.updated` goes to message authors, coalesced and rate-limited (*policy*). In a DM it carries the reader's position `{conversation_id, reader_id, read_seq}`; in a group, `{conversation_id, up_to_seq, read_by_count}` (DM-009).
- `user.join_request_resolved` goes to the requester: `{conversation_id, request_id, outcome: "approved" | "declined"}` (GRP-006).

## 4. Error model

Each error is `{"error": {"code": "<stable_snake_case>", "retryable": bool, "retry_after_ms"?: n, "detail"?: {...}}, "server_time": "…"}` with a matching HTTP status. Stable codes: `unauthenticated`, `session_revoked`, `not_found` (also used for unauthorized object access, XC-1), `forbidden_action` (a member lacking a right), `payload_invalid`, `too_large`, `rate_limited`, `operation_conflict`, `revision_conflict`, `invite_invalid`, `cursor_expired`, `upgrade_required`, `unavailable`. Across the WASM boundary the same codes become a TS discriminated union `{ kind: code, … }`. The binding generator must produce that union, and PT-01 checks it.

- `session_revoked` carries `detail.reason`, with the values of `user.session_revoked` (§3).
- `invite_invalid` covers every unknown, used, expired or revoked single-use token: an org invite, an invite link, the bootstrap token or a password-reset link.
- `cursor_expired` carries `detail.stream`: `"conversation"` (with `detail.conversation_id`) for an event page with `after < min_retained_seq − 1`, or `"user"` for `GET /v1/sync` with `user_cursor < min_retained_user_seq − 1` (§2.2). The client then runs that stream's reset ([sync.md §4](sync.md#4-catch-up-and-realtime)).
- `operation_conflict` means the `operation_id` was already used under the same key for a different command, whatever its kind or target (§2.1).
- `unavailable` (retryable) also covers PostgreSQL deadlock (`40P01`) and serialization failure (`40001`) once the server has retried the transaction up to 3 times with jitter. The lock order that keeps these rare is in [sync.md §3.1](sync.md#31-lock-order-user-sequence-and-retries).
- When several checks fail, the write-path order in [sync.md §3](sync.md#3-server-write-path-durable-ack) decides which code is returned (for example `session_revoked` wins over a duplicate).
- How the client outbox treats each code is in [sync.md §5](sync.md#5-client-outbox-and-pending-state). The TS union also carries client-only reasons, such as `dependency_failed`, that never appear on the wire.

## 5. Contract fixtures (P0 acceptance)

For each driving adapter and each P1 use case there is a golden fixture set under `crates/rem-protocol/fixtures/v1/`, created in P1-04. It covers: (1) a valid command and its ACK, (2) a denial (`not_found` for a non-member, `forbidden_action` for a missing right), (3) for each use case that §2.1 marks idempotent, a retry with the same `operation_id` returning `duplicate: true` (for a pre-session command, the stored result with `duplicate: true` and no session), and (4) a version mismatch giving `upgrade_required`. Both server tests and client SDK tests consume the same fixtures, which is how drift is caught. Fixture changes are reviewed like schema changes ([testing-ci.md §3](../engineering/testing-ci.md#3-impact-map-and-selection)).

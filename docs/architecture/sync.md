## 2. Identifiers

- `operation_id`: a UUIDv4, generated by the client per user intent, stored with the pending op and reused for every retry.
- `message_id`, `event_id`: UUIDv7, assigned by the server. `conversation_id`, `user_id` and `device_id` (server-assigned at a store's first login, §5.4): UUIDv7. IDs are never sequential integers on the wire (SEC-003).
- `seq` (per conversation) and `user_seq` (per user): server-assigned `u64`.

## 3. Server write path (durable ACK)

1. The driving adapter authenticates the session and builds `Actor`, plus `operation_id`, and decodes the v1 DTO.
2. The `SendMessage` use case validates the payload (size, entities, attachments) and builds the canonical command ([contracts.md §2.1](contracts.md#21-idempotent-mutations-and-operation-lookup)) **before** opening the transaction. The idempotency hash covers that canonical command, never the request bytes, so a retry that a newer client encodes differently still matches.
3. `ConversationLog::append` runs a single PostgreSQL transaction at READ COMMITTED. The order of the steps decides which outcome wins when several apply:
   1. **Session.** `SELECT … FROM sessions WHERE id = $1 FOR SHARE`, in its ascending place among the session rows the command locks (§3.1), not before them. A revoked session returns `session_revoked`, even for a duplicate. A pre-session command skips this step (§3.2).
   2. **Lock.** `SELECT … FROM conversations WHERE id = $1 FOR UPDATE`. This serializes all writers of this conversation: sends, edits, deletes, pins, and membership and permission changes.
   3. **Idempotency.** Look up the record by its key (I2). The same kind, target and hash return `Duplicate`, which carries only the stored original ACK fields and no new data, even if the actor's membership was removed since. A different kind, target or hash returns `Conflict` (`operation_conflict`), wherever the id was first used.
   4. **Right.** For a new operation only, check the actor's current membership and right (send, send_media…).
   5. **Write.** `UPDATE conversations SET last_seq = last_seq + 1 RETURNING last_seq`, which gives the gap-free seq (I3). Insert the message, the event `(conversation_id, seq)`, the idempotency record, the outbox row and the search-index row, plus any user events (§3.1).
   6. Commit.
4. Only after the commit does the adapter reply `ack {operation_id, message_id, conversation_id, seq, server_time}`.
5. The outbox is dispatched in seq order per conversation (§3.3). Delivery is at-least-once, and a crash re-claims the work.

**Serialization of revocation versus send:** removing a member takes the same conversation row lock and appends `member.removed` at some `seq = r`. Any send committed earlier has `seq < r`, so the removed member was authorized for it and may receive it. Any later send has `seq > r`, and I4 denies it. A retry of an earlier send after the removal is a duplicate and gets only its stored ACK. A **session** revocation updates the session row, so it waits for the share locks of that session's in-flight commands, and commands that reach step 1 later wait for it and then see the revocation. Each command therefore either commits before the revocation commits or returns `session_revoked`; no command of a revoked session commits after the revocation. `Fanout` stops pushing to the session at the revocation commit and closes its sockets (§3.3). Tests (PT-02, `pg` integration): a duplicate after a removal returns the stored ACK and nothing else; a send racing a revocation either commits first or gets `session_revoked`; a duplicate after the revocation gets `session_revoked`.

**Throughput note:** the row lock limits each conversation to one writer at a time. That is intended for ordering. PT-02 measures sends per second per hot conversation on the reference hardware, and the group-size and slow-mode policy (GRP-010, P2) uses that number.

### 3.1 Lock order, user sequence and retries

- **`user_seq`.** Each user row holds `last_user_seq`. A transaction that writes a user event runs `UPDATE users SET last_user_seq = last_user_seq + 1 WHERE id = $1 RETURNING last_user_seq` in the same transaction, so the user stream is gap-free like the conversation stream (I9).
- **Lock order.** Every transaction takes row locks in one global order:
  1. device rows, in ascending id, then session rows, in ascending id. The actor's own session takes its place in this sequence, `FOR SHARE`, or `FOR UPDATE` when it is itself being revoked; revoked sessions are locked `FOR UPDATE`;
  2. approval rows;
  3. org invite rows and password-reset link rows;
  4. conversation rows, in ascending id;
  5. link and join-request rows;
  6. user rows, in ascending id;
  7. attachment rows, in ascending id.

  Dispatch-cursor rows (§3.3) are locked only by dispatcher transactions, which lock nothing else. A transaction that learns from a read which rows it must lock takes them in this order and then re-validates what it read. Examples: a forward from A to B locks both conversation rows in id order; group creation locks the new conversation, then the members' user rows ascending; a membership change locks the conversation, then the affected users' rows. Two admins revoking each other's sessions lock both session rows in the same ascending order, so they cannot deadlock: the one that waits then sees its own session revoked and returns `session_revoked`. Login locks the device row `FOR UPDATE` (for a login without `device_id`, the row found or created for its `device_nonce`, §5.4), then that device's previous session `FOR UPDATE`, then the user's row `FOR UPDATE`. It verifies the password (Argon2id, ADR-0010) before its transaction and never under a lock; under the user row lock it re-checks only the credential version (the id of the hash it verified) and the account status, restarting and verifying again if the version changed and failing on a non-active status; so two concurrent logins for one device leave one unrevoked session. Eviction recovery (`DELETE /v1/sessions` with reason `device_lost`) likewise locks the device row before the session row, so it cannot deadlock with a login on that device. An admin-delivered reset revokes the target's sessions at redemption (`password_reset.redeem`, T27), never at issue or approval: the redemption reads the link's user, locks that user's session rows, then the link row, and re-validates the link. **Revoke-all.** A transaction that revokes all of a user's sessions (reset redemption, password change, deactivation, admin session revocation) reads the user's unrevoked sessions again after it takes the user row lock. If that read finds a session outside the set it locked, which a login committed in between, it rolls back and restarts, as a login does. A login that waits on the user row then sees the new credential version or status, so it restarts against the new password or fails, and no session of the old credential stays live.
- **Retries.** The server retries a transaction that fails with PostgreSQL `40P01` (deadlock) or `40001` (serialization failure) up to 3 times with jitter, then returns `unavailable`, which the client retries ([contracts.md §4](contracts.md#4-error-model)). This retry is a backstop; the lock order keeps these failures rare. PT-02 measures large-group membership transactions, which lock one user row per member, and tests mutual session revocation by two admins ([E-17](../plan/evidence.md#e-17-p0-pt-02-postgresql-sequencing-spike)). A login racing a reset redemption, a password change and a deactivation (no live session remains) is tested in P1-03 (LD-45).
- **Durability.** The application role runs with `synchronous_commit=on`, set on the role and checked by the server at startup. I1 depends on it: with asynchronous commit an ACK could precede durability.

### 3.2 Idempotency for every mutation

The mutation table in [contracts.md §2.1](contracts.md#21-idempotent-mutations-and-operation-lookup) is the only list of mutating commands. For each endpoint it names the command kind, the serializing row, the idempotency key and the canonical fields, or the reason the command is not idempotent. Every idempotent command follows the order of §3: session check, lock of its serializing row (in the order of §3.1), idempotency lookup, right check, effect. Its idempotency record (kind, target, canonical hash, stored result) is written in the same transaction as the effect (I2).

- **Serializing row.** A command that changes a conversation's log or membership locks that conversation's row, so link redemption, which adds a member, serializes with every other writer of that conversation. A command that changes only the actor's own state (read position, prefs, delete for self) locks the actor's user row.
- **Pre-session commands** (bootstrap, invite redemption, password-reset redemption) run before any session exists. They skip the session step and key their record by `(token_hash, operation_id)`, where the token is the redeemed credential (an org invite may allow several uses, each under its own `operation_id`). The stored result never holds a secret or a session. A replay returns it with `duplicate: true` and no session, and the client then logs in (§5.4). The same `operation_id` with a different token is a different key and therefore a new command: an `operation_id` is unique only within its key. `GET /v1/operations` serves session commands only, so a pre-session op settles by replay. The idempotency lookup comes before the token check, so a replay returns the stored result although the token is now used. Once the record is pruned (§7), the same request gets `invite_invalid` although the op took effect; an automatic retry never meets that, because it stops at `IDEMPOTENCY_TTL − SAFETY_MARGIN` (§5.3), and after a confirmed retry the client treats `invite_invalid` as "may already be done" and offers the login.
- **Not idempotent.** Login issues a fresh session on each attempt and revokes the device's previous session (§5.4), so a lost response leaves no orphan session. A login without a `device_id` (a first login, eviction recovery) carries the store's `device_nonce`, and the server registers at most one device per `(user_id, device_nonce)`, so a retry binds to the same device and revokes its earlier session. Two concurrent first logins with one nonce collide on that unique key, and the loser rolls back and re-runs once. The table gives the reason for every other command that is not idempotent.
- **Created targets.** When a command creates its target (for example create group, open DM, attachment create), the record's `target` is the created id, written after creation, and the conflict check compares kind and canonical hash only.
- **Concurrent duplicates.** Commands that create their target have no row to lock. Two concurrent duplicates collide on the unique idempotency key: the loser's transaction rolls back on the unique violation and re-runs once, and the re-run finds the record. The same re-run settles one `operation_id` reused on two targets at once.
- **Open DM.** A DM pair is unique per organization (index in [architecture.md §4](architecture.md#4-domain-model-sketch-validated-against-invariants-not-a-final-schema)). Opening an existing DM returns it. When two actors open the same DM at once, under different keys, they collide on that index: the loser's transaction rolls back on the unique violation, re-runs once and returns the winner's conversation with `created: false`.
- **Self conversation.** It is created with the account, in the transaction that creates the account (bootstrap, invite redemption, admin account creation), one per user. No endpoint creates it.
- **Read position.** The server clamps the position to the reader's highest visible seq (§6.1) and keeps the maximum (I7). A coalescing worker writes `receipt.updated` for message authors at a *policy* rate, outside the read transaction, so a read locks only the reader's user row.

### 3.3 Push path: ordered dispatch and fanout authorization

- **Ordered dispatch.** Each conversation has a dispatch cursor row. A dispatcher claims cursor rows with `FOR UPDATE SKIP LOCKED`, reads that conversation's outbox rows after the cursor in seq order, hands them to `Fanout`, and advances the cursor in the same transaction. Seqs commit in order under the conversation lock, so the rows after the cursor have no holes. One dispatcher at a time owns a conversation, so its pushes leave in seq order. A crash releases the claim, and the next dispatcher resends from the cursor (at-least-once). The user stream uses the same scheme with a cursor per user.
- **Per-event authorization.** For each event and each recipient session, `Fanout` pushes only if the recipient's current membership interval contains the event's seq and the session is not in the revocation set. The payload scope follows §6.2. Both checks read an in-memory authorization cache on the single P1 node, which membership changes and session revocations update synchronously at commit, before the command is acknowledged. Because `member.removed` at `r` holds the conversation lock until it commits, the cache already excludes the member when `r + 1` commits. Multi-node fan-out needs a shared mechanism (SYN-012, P2).
- **Cache updates and commit errors.** A removal or revocation is applied to the cache just before `COMMIT` and is never reverted blindly. Each membership entry carries the seq of the membership event that wrote it, and a write applies only if its seq is higher, so a late post-commit addition never overwrites a later removal's denial. A rebuild is exempt from that guard: it replaces the affected entries unconditionally, which also clears a pre-commit denial whose transaction aborted (an aborted removal consumes no seq, I3), and tags each entry with the conversation's `last_seq` read under its lock. A revoked session entry is terminal: only a rebuild re-admits it. On any commit error, including an unknown outcome (the connection is lost during `COMMIT`), the affected entries (that conversation's memberships, that user's sessions) stay denied, and the server rebuilds them from the database once it answers. A rebuild locks the conversation row `FOR SHARE` (for a revocation, that user's session rows `FOR SHARE`, in §3.1 order), reads and installs the entries under that lock and then releases it, so it waits out the unresolved transaction and any in-flight removal or revocation and sees only committed outcomes. A removal or revocation that starts after the rebuild waits for that lock to be released, so the denial it applies before its `COMMIT` is never cleared by a rebuild that started earlier. An addition is applied only after a confirmed commit, or by that rebuild. A send that commits between the addition's commit and its cache entry is not pushed to the new member; the member's client fetches it after `user.membership_changed` (§4.1). A commit error therefore never re-admits a removed member or a revoked session (I10); it can only deny a push spuriously. After a rebuild, `Fanout` sends a `head {conversation_id, last_seq}` frame ([contracts.md §3](contracts.md#3-event-catalog-conversation-stream-unless-noted-all-schema_version-1)) to every still-authorized connected session of each affected conversation (for a session revocation, that user's conversations), so gap detection (§4.1) repairs a spurious denial without waiting for a reconnect.
- **Tickets and sockets.** Redeeming a WS ticket re-checks that the session is valid and not revoked. At the revocation commit, `Fanout` stops pushing to the session and closes its sockets.
- **Tests:** a removed member never receives `r + 1` over push; a revoked session receives no push after the revocation commit; after a removal or revocation whose commit outcome is unknown, the entries stay denied until the rebuild, and the rebuild sends `head` to the sessions still authorized; a removal that commits after a rebuild started stays denied; an addition racing a later removal never re-admits the member; after an aborted removal the rebuild re-admits the member, who then receives `head` and later pushes; two dispatchers never interleave one conversation.

## 4. Catch-up and realtime

- **User stream:** `GET /v1/sync?user_cursor=U&limit=N` returns user events after `U`, plus `conversation_heads` (conversation_id → last_seq). Heads cover current memberships. They also include a final head `{conversation_id, last_seq: left_seq − 1, left: true}` for each conversation whose leave event (`user.membership_changed`) has a `user_seq` above `U`. Once the device's cursor reaches that event, the head is gone. So before the client persists `local_user_seq` at or past a leave event, it catches that conversation up to `left_seq − 1`, or durably marks the conversation as owed up to that seq and catches up later; a push dropped before the leave is therefore still fetched. When that catch-up gets `not_found` on the event page or the state read, the conversation was deleted after the leave: the client clears the owed mark and marks the conversation deleted, so the cursor can advance. A conversation has at most one head: its current head while the user is a member, otherwise a final head at the latest leave, so leaving several conversations gives one final head each. The final head reveals nothing after the leave, and a cursor below the user-stream floor gets `cursor_expired` (below), so retention bounds the listing. For each head ahead of its cursor, the device then pulls `GET /v1/conversations/{id}/events?after=C&limit=N` from its `covered_through` cursor `C` (§4.1). Wire form: [contracts.md §2.2](contracts.md#22-visible-ranges-event-pages-and-redacted-stubs). Tests: SYN-006.d.
- **WebSocket** (`rem.v1` subprotocol) is a notification path only. It pushes `{conversation_id, seq, event}` (or `{user_seq, user_event}`), and `head {conversation_id, last_seq}` frames after a cache rebuild (§3.3). The client applies a conversation event only when its seq is the next visible seq (§4.1), and a user event only when `user_seq == local_user_seq + 1`. A higher seq is a **gap**: buffer it and range-fetch. A lower or equal seq is a duplicate: ignore it (I5). A `head` frame is handled like a conversation head: the client range-fetches when a visible seq lies above its `covered_through` and at or below `last_seq`.
- **Reconnect:** fetch a WS ticket over HTTPS, connect, send `hello {protocol, client_version, device_id, user_cursor}` (the server rejects a `device_id` other than the session's bound device), run catch-up to the heads, then trust pushes. Backoff is exponential with full jitter, capped at *policy* (default 60 s).
- **Retention floors:** each conversation exposes `min_retained_seq`, and each user exposes `min_retained_user_seq`; pruning raises both (§7). An event page request with `after < min_retained_seq − 1` returns `cursor_expired`, and the client runs the conversation reset. `GET /v1/sync` with `user_cursor < min_retained_user_seq − 1` returns `cursor_expired` with `detail.stream = "user"`, and the client runs the user-state reset. Both resets keep the pending ops and re-submit them, and the UI shows a notice (CLI-011).
- **Conversation reset:** the client reads the conversation state (`GET /v1/conversations/{id}`), the roster (`GET …/members`, all pages, each with `as_of_seq`) and the newest history page through the read endpoints ([contracts.md §2](contracts.md#2-http-surface-p1-v1)). At the start of the reset it drops the cached roster, events and message projections of that conversation, once; message rows return only from history pages and from events applied after `covered_through`. It sets `covered_through` to the state's `last_seq`. A roster page applies as is only if its `as_of_seq` ≥ `covered_through`; otherwise the client also re-applies the member events in `(as_of_seq, covered_through]`, fetched with an event page when not cached. Older history is re-fetched page by page on scroll. The roster and history pages may be newer than the state; catch-up from `covered_through` then re-applies the overlapping events, which is idempotent (I5). A former member's reset reads the capped state and history pages only (§6.1), because the roster returns `not_found` to them (authorization per endpoint: [threat-model.md §4](../security/threat-model.md#4-authorization-matrix-p1)).
- **History pages** (`GET …/messages?before=<seq>&limit=N`; parameters, order, tombstones, `as_of_seq` and `next_before` in [contracts.md §2.2](contracts.md#22-visible-ranges-event-pages-and-redacted-stubs)): a page holds only the reader's visible messages, references follow §6.2, and a former member's content follows §6.1. A page is authoritative for its span, the creation seqs in `[next_before, before)`, where a `null` `next_before` stands for seq 1 and an absent `before` for `as_of_seq + 1`: the client drops any cached message row in that span that the page omits. Edits, deletes and hides from a pruned window therefore reach old cached rows. A page row never lowers a cached revision, a cached tombstone is terminal, and a hide for self applied locally stays, so a page read before a later push cannot undo it. When a page's `as_of_seq` is below `covered_through`, the client also re-applies the events in `(as_of_seq, covered_through]` to the page's rows, or refetches the page.
- **User-state reset:** the client pages `GET /v1/conversations`. Each entry carries the user's membership (`joined_seq`, `left_seq`, and the interval's `history_visibility`), `visible_ranges`, `last_seq`, `read_seq` and prefs, and each page carries `as_of_user_seq`, read in the same snapshot as the page's entries. The client replaces its cached user state from these entries and sets `local_user_seq` to the smallest `as_of_user_seq` it received. User-event payloads hold absolute values, so replaying the overlap from there is idempotent (I5). It then runs the conversation reset for every cached conversation. A cached conversation missing from the list is read with `GET /v1/conversations/{id}`: a former member gets the capped state (§6.1), and a deleted conversation returns `not_found` and is marked deleted. Cached profiles are marked stale and refetched on display. Messages hidden for self need no separate step, because history pages omit them. User state with no read path is dropped: cached own pending join requests (a pruned `user.join_request_resolved` would leave them stale; an approved one shows as a membership) and group receipt counts, which return with the next `receipt.updated`.

### 4.1 Cursors and gap detection

- The cursor per conversation is `covered_through`: every seq up to it is either applied or outside the reader's visible ranges (§6.1). An event page reports the span it covers, and the client stores its `covered_to` ([contracts.md §2.2](contracts.md#22-visible-ranges-event-pages-and-redacted-stubs)). A former member's pages are capped at their final leave (§6.1).
- The **next visible seq** is the smallest seq above `covered_through` that lies inside a visible range. Gap detection applies only there: a jump across an invisible range is not a gap. Inside a visible range a current member receives every seq, as a full event or a redacted stub (I11), so a gap always fills.
- The initial cursor is the start of the first visible range minus 1. On a rejoin, `user.membership_changed` gives the new `joined_seq` and `history_visibility` ([contracts.md §3](contracts.md#3-event-catalog-conversation-stream-unless-noted-all-schema_version-1)). The client refreshes `visible_ranges` from the conversation state before it resumes gap detection, and then pulls event pages up to the conversation's `last_seq`. When the refresh adds visible ranges below `covered_through` (a rejoin under `full`), the client lowers `covered_through` to the lowest added start minus 1 and pages again. Events it applied before are duplicates (I5), and a cursor below the floor resets (§4).

## 5. Client outbox and pending state

States: `pending → sent (ACK or own event seen) → read`; `pending → failed(permanent | conflict | expired | stuck | dependency_failed)`, which offers retry or discard; and `pending → paused` while the queue waits for a login or an upgrade (§5.1).

| Situation | Behavior |
|---|---|
| Send while offline | Persist (I6), show pending, queue in per-conversation FIFO. |
| Lost ACK | On retry, the server returns `Duplicate(stored)` with the same `message_id`. Alternatively, catch-up delivers an event carrying our `operation_id`, or `GET /v1/operations/{operation_id}` returns the stored ACK ([contracts.md §2.1](contracts.md#21-idempotent-mutations-and-operation-lookup)). Either settles the pending op without a resend. |
| Error response or transport failure | Handled by its class (§5.1). |
| Op references a local message that is not yet ACKed | Waits for the source op while it is pending, and ends with it if the source ends without an ACK, also when the source had already ended (§5.2). |
| Op too old, or failing repeatedly | `expired` or `stuck` (§5.3). |
| Logout | The client warns when unsent ops exist, then revokes the session, clears the credentials and deletes that user's local store (§5.4). |
| Revoked or expired session, or another user signs in without a logout | The store goes dormant, and its ops resume only when the same user signs in again on that device (§5.4). The UI says that the unsent items were not delivered yet and will be sent after that user signs in again. |

### 5.1 Error classes

Every code in [contracts.md §4](contracts.md#4-error-model) maps to one outbox class.

| Class | Codes | Outbox behavior |
|---|---|---|
| Retryable | `unavailable`, network failure or timeout, `rate_limited` | Back off with full jitter; `rate_limited` waits at least `retry_after_ms`. The conversation FIFO stays blocked, so the user's order is kept, until the op succeeds or becomes stuck (§5.3). |
| Permanent | `payload_invalid`, `too_large`, `forbidden_action`, `not_found`, `invite_invalid` | Mark `failed(permanent)` with the reason and unblock the FIFO. Dependents fail (§5.2). |
| Reconcile | `operation_conflict` | Fetch `GET /v1/operations/{operation_id}`. If the stored kind and target are this op's (the kind alone for a command that creates its target, §3.2), the stored ACK settles it and the server's version is shown; otherwise mark `failed(conflict)`. Never resend under a new id automatically; only a user retry of `failed(conflict)` mints one (§5.2). |
| Reconcile | `revision_conflict` | Show the conflict UI with the returned current revision; no automatic merge. The user's resolution is a new op. |
| Session-terminal | `unauthenticated`, `session_revoked` | Stop the queue and require login. The store goes dormant (§5.4). Its ops resume under their original `operation_id` after the same user signs in again on that device; the new session binds to the stored `device_id`, so a lost-ACK op deduplicates (I2). |
| Paused | `upgrade_required` | Keep the ops and show the upgrade screen. After the upgrade they resume under their original `operation_id`; the canonical hash makes a re-encoded retry a duplicate, not a conflict (§3). |
| Sync-reset | `cursor_expired` | Run the reset that `detail.stream` names (§4), then continue the queue. |

### 5.2 Dependent operations

- An edit, delete, pin, reply or forward that references a local message whose send is not yet ACKed depends on that send. It waits for the source ACK, even when the source is in another conversation's queue, and keeps its own FIFO position meanwhile. When the ACK arrives, the client rewrites the reference from the local id to the server `message_id` before the dependent's first attempt.
- An edit or delete of a message whose send has not been attempted yet is folded into the pending send locally: an edit replaces the body and a delete drops the send. After the first attempt the server may already hold the message, so a later edit or delete becomes a dependent op.
- When a source op leaves `pending` without an ACK, its dependents take a terminal state with it, transitively: a `stuck` source makes them `failed(stuck)`, an `expired` source makes them `expired`, and any other failure, a discard, or a folded delete (which discards the send) makes them `failed(dependency_failed)`. A dependent therefore never waits longer than the stuck bounds of its source and of the ops ahead of that source, each bounded by §5.3, and its queue then continues. A dependency always points to an earlier op, so dependencies cannot form a cycle. An op created while its source is already `failed` or `expired` (for example an edit, reply or forward of a failed bubble) takes the same cascade state at once and never holds a FIFO position; only a retry of the source re-queues it.
- A source that left `pending` without an ACK can still be settled later, by its own event or its stored result (§5, Lost ACK). It then counts as ACKed and shows as sent. Its failed dependents stay failed and are not re-queued on their own; a user retry of one rewrites its reference to the server `message_id` and re-enters it at the tail of its FIFO.
- A user retry of a failed op re-enters at the tail of its conversation FIFO, and the dependents that failed with it re-enter after it, each at the tail of its own conversation FIFO. A retry of a dependent alone, while its source is neither pending nor ACKed, fails it again at once with the state the cascade above gives; only a retry of the source re-queues it. A user retry reuses the op's `operation_id`, so a lost-ACK attempt still deduplicates (I2), except after `failed(conflict)`, where the id belongs to another command and the retry mints a new one. Test cases are in the SYN-007 row of [backlog.md §4](../plan/backlog.md#4-p1-traceability-matrix-84-ids-lifecycle-all-specified).

### 5.3 Expiry and stuck operations

- **Server-time age.** Each pending op stores `created_after`, the `server_time` of the latest response the client saw before it created the op; a store always has one, from its first login. Before any automatic retry the client holds a fresh `server_time`: one from a response received after the latest reconnect and less than `SAFETY_MARGIN` ago by monotonic time; otherwise it refreshes it first. Reconnect catch-up comes first, and on resume from suspend the client reconnects before any retry, because monotonic clocks may pause during sleep. The op's age is that fresh server time minus `created_after`. No device clock is involved, so a clock change while the device is offline cannot shorten the age. It can only overestimate it, which leads to a confirmation, never a duplicate. The client also persists the latest offset between `server_time` and its own wall clock, and uses it only for display and for the stuck bound.
- **Expiry.** Automatic retry stops when the age reaches `IDEMPOTENCY_TTL − SAFETY_MARGIN` (*policy*, default margin 2 days). The op becomes `expired` and shows "needs confirmation". A confirmed retry reuses its `operation_id`, so it still deduplicates while the server holds the record (§7); after that it may duplicate, which the confirmation says (R-03). Test: with the client clock skewed by ±24 h (SYN-014), or changed while the device is offline, no op is retried automatically after its server record is gone.
- **Stuck.** A retryable op that has failed N attempts (*policy*, default 20) or has kept failing for T (*policy*, default 24 h), measured in server time from its first failed attempt, becomes `failed(stuck)`, with retry and discard. No attempt is made, and none counts toward N or T, while the transport is offline or the queue is paused; only failures with the connection up count. For a failure with no server response, T uses the persisted offset, so a wall-clock jump while online can skew T; N still bounds the wait. An op that has not been attempted is never itself stuck: it waits behind its FIFO head and its source, each bounded here, so its wait is at most the sum of the bounds ahead of it, and it fails early only through its source (§5.2). Its dependents become `failed(stuck)` with it (§5.2). Its conversation FIFO then continues, and the UI says that the order may differ ([ux.md §2](../product/ux.md#2-state-model-shown-to-users)).

### 5.4 Store identity and browser storage

- The local store is keyed by `(instance, user_id, device_id)`. An outbox is drained only under a session of the same user and device (I12).
- **Device binding.** Before its first login, a store persists a client-generated `device_nonce` (UUIDv4) and sends it with `POST /v1/sessions` whenever it has no bound `device_id`. `device_id` is server-assigned (UUIDv7) at a store's first login, at most one per `(user_id, device_nonce)`, so a retried first login after a lost response binds to the same device and revokes that device's earlier session. It lives in the store and is sent in `hello`. `POST /v1/sessions` carries the stored `device_id`: if it is registered to that user and not retired, the new session binds to it; otherwise the server registers a new device and returns its id, with no error, so the call is no oracle. Each session has one device, and creating a session for a device revokes that device's previous session (reason `replaced`). `device_id` is therefore stable across a re-login, and I2 deduplicates a lost-ACK op across a revocation.
- **Device mismatch.** When the login response returns a `device_id` other than the stored one (the device is retired or unknown), the client opens a new store and never drains the old outbox (I12). It moves the old ops into the new store as "needs confirmation" and then deletes the old store: a confirmed retry gets a new `operation_id` and may duplicate, which the confirmation says.
- **Logout.** An explicit logout revokes the session and clears the credentials. When unsent ops exist the client warns first ([ux.md §2](../product/ux.md#2-state-model-shown-to-users)), and it then deletes that user's local store, unsent ops included (ID-002.b). The deletion does not wait for the revoke: when the revoke gets no response (offline), the store and credentials are deleted anyway, nothing is retried, and the session stays live on the server until it expires or is revoked from the session list.
- **Dormant store.** A revoked or expired session, or another user signing in without a logout, leaves the store dormant. Its ops resume only when the same user signs in again on that device (ID-003.c). This is the interim default of **PO-Q10** ([decisions.md §3](../plan/decisions.md#3-po-question-queue)). A dormant store stays readable to anyone using that browser profile or OS account, which threat-model T20 discloses ([threat-model.md §3](../security/threat-model.md#3-threats-and-mitigations-stride-messaging-specific)).
- **Browser** (decided in ADR-0003 after PT-01): there is one device per user per browser profile and origin. A single writer drains the outbox across tabs (Web Locks or a SharedWorker / dedicated worker). The client calls `navigator.storage.persist()` and reports the persistence state in diagnostics. Clearing site storage, or eviction, loses unsent ops and the device identity.
- **Eviction recovery.** If the store marker is missing while a session cookie exists, the client revokes its current session, reports "local data was cleared; unsent messages lost", and requires a login without `device_id` from a new store with a new `device_nonce`, which registers a new device. The old device is retired (reason `device_lost`) and is never bound again. That loss is disclosed in the UI and in the docs. PT-01 measures eviction.
- **Tests** (backlog ID-002, ID-003 and SYN-007): a re-login keeps `device_id` and a lost-ACK op then deduplicates; a retried first login after a lost response leaves one device and one live session; switching users; eviction recovery.

## 6. Revocation and history authorization

- Membership intervals: rejoining opens a new interval. Each interval records the group's `history_visibility` (`full` or `from_join`, a *policy* default per group) when it opens, so the setting applies to new members and to later rejoins (GRP-007.a). The intervals turn into visible ranges (§6.1).
- A removed member keeps the history already synced to their device (reference-like), including attachment copies already on it. Remote purge on removal is an org-policy candidate (SEC-005, P3). The removed member's server reads are capped at `left_seq` (§6.1), and they get no new attachment URL through a conversation they left (MED-010.c, T6). Authorization per read endpoint: [threat-model.md §4](../security/threat-model.md#4-authorization-matrix-p1).
- Admin deactivation revokes all sessions and closes their sockets.

### 6.1 Visible ranges

The server computes a reader's `visible_ranges` per conversation, as half-open `[from_seq, to_seq)` ranges (wire form in [contracts.md §2.2](contracts.md#22-visible-ranges-event-pages-and-redacted-stubs)), from their membership intervals:

- An interval opened under `full` grants `[1, its end)`: the history before the join, including periods when the member was absent before a rejoin, up to the interval's end.
- An interval opened under `from_join` grants `[joined_seq, left_seq)`.
- `visible_ranges` is the union of the grants. A `history_visibility` change is a sequenced `conversation.updated` and changes no existing interval, so no reader's ranges change with it.
- A former member keeps the grants of their intervals, which end at their last `left_seq` at the latest. Nothing at or after `left_seq` is visible (SYN-009). Their event pages report `last_seq` and `covered_to` capped at `left_seq − 1` of their final leave, and a request past that returns an empty page with the same caps, so paging ends and no later progress leaks. Their state, event pages and history pages show content as of `left_seq − 1`: each message at its last revision committed before `left_seq`, and pins and settings as of that seq. No edit, pin or setting change made at or after `left_seq` reaches them. A message deleted for everyone, at any time, is a tombstone with no deletion time, because deletion removes the content from the primary store (DEV-04); event pages carry it in place of the original events ([contracts §2.2](contracts.md#22-visible-ranges-event-pages-and-redacted-stubs)).

Every read path applies these ranges: event pages, history pages, conversation state, search, attachment URLs and push. A reader's ranges change only with their own membership (§4.1).

### 6.2 Referenced messages and scoped events

- **Referenced messages.** An event that references a message (`message.edited`, `message.deleted`, pins, reply quotes, forward sources) is visible to a reader only when the referenced message's creation seq is visible to them, not merely the event's own seq. Otherwise an edit, delete or pin event arrives as a redacted stub, and a reply keeps its own body while its quote becomes unavailable. A forward keeps its body and its original author (`forwarded_from.author_id`, DM-005.a, unless *policy* hides attribution, DM-005.d); only its source conversation and message ids become unavailable. The UI renders an unavailable reference as "Message unavailable" ([ux.md §2](../product/ux.md#2-state-model-shown-to-users)). A request naming an invisible message id returns `not_found`. Wire forms: [contracts.md §2.2](contracts.md#22-visible-ranges-event-pages-and-redacted-stubs).
- **Attachments.** An attachment is downloadable by a current member who can see at least one undeleted message that references it, by the rule above (MED-010.a). A former member gets no new URL through a conversation they left; access through a conversation where they are a current member follows this rule (MED-010.c, §6).
- **Scoped events.** No event carries an invite-link token. Link events carry their payload only to holders of the link right, and join-request events only to holders of the approve right. Other current members receive a redacted stub at that seq, so contiguity holds (I11). Payload contents: [contracts.md §3](contracts.md#3-event-catalog-conversation-stream-unless-noted-all-schema_version-1).
- **Read positions.** The server clamps a read position to the reader's highest visible seq (I7).

## 7. Evolution, retention and clocks

- Event payloads carry a `schema_version` per type. Additive fields keep the version, and clients ignore unknown fields. Removing or changing the meaning of a field means a new version, and the server emits both versions during the compatibility window (current + previous minor, SYN-013).
- An unknown event type is stored as `unsupported` and shown as a placeholder. If the server says `min_client_version` is above ours, the client shows the upgrade screen.
- The event log is pruned past `EVENT_RETENTION` by a pruning job, which also raises `min_retained_seq` and `min_retained_user_seq` (§4) to the lowest seq still retained, or to `last_seq + 1` (`last_user_seq + 1`) when every event of that stream is pruned, so a stale cursor gets `cursor_expired`, never an empty page. Messages persist per message retention. Storage numbers come from PT-02. The settings and the job are listed in [operations.md §2](../operations.md#2-configuration-and-secrets).
- The server prunes an idempotency record `IDEMPOTENCY_TTL + SAFETY_MARGIN` after its own commit time, by server time. Clients stop automatic retry when an op's age reaches `IDEMPOTENCY_TTL − SAFETY_MARGIN` (§5.3). The age counts from `created_after`, which never follows the commit, and is never underestimated. The record is therefore still held when the last automatic retry arrives, unless that retry arrives more than `2 × SAFETY_MARGIN` after its fresh `server_time`.
- Server time is authoritative for display timestamps and for op age (§5.3). Timeouts use monotonic clocks, and wall time serves only display and the offset estimate (`Clock` in [architecture.md §3.3](architecture.md#33-client-ports-owned-by-rem-client-core)). A test clock lives in `rem-test-support`.

Still open here, and candidates for that register:

- The defaults for `SAFETY_MARGIN`, the stuck bound (N, T) and the receipt coalescing rate, to be confirmed by PT-01 and PT-02 measurements.
